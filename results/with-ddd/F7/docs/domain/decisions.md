# Decision log

Append new decisions at the end. Never rewrite or delete an entry; when a decision changes, add a new entry that says which one it replaces.

| # | Decision | Why |
|---|---|---|
| D1 | The domain is split into aggregates: User, Building (with its Classrooms), Course, Student, Professor and Section (with its Enrollments). | Each aggregate protects its own invariants; the Enrollments of a Section are what its Capacity limits. |
| D2 | Between aggregates, references are by identity (Course code, `ClassroomRef`, Professor ID, Student number), never by object. | A modified Course or Professor shows its new data everywhere (R26) without copies to keep in sync. |
| D3 | A Building has an internal `BuildingId` that never changes, and `ClassroomRef` uses it. The name is only what people type and see. | The name of a Building can change (R18); Sections must keep pointing to the same Classroom. |
| D4 | The rules most likely to change are policy objects: `Permissions`, `SectionChoicePolicy` and `GradeScale` (`policies.md`). | A change to one of those rules should touch one class and its tests. |
| D5 | Cross-aggregate rules (references that block deletion, Capacity against Enrollments, one Enrollment per Course) live in the application services, which ask the repositories. | No aggregate can see the others; the use case can. |
| D6 | Application services check everything first and change the aggregates last (I21). | An Instruction that fails must change nothing (R38), without undo logic. |
| D7 | Repositories are interfaces in the domain and in-memory classes in `enrollment.infrastructure`, built on `java.util` collections. | The data lives in memory (R2); the domain does not depend on how it is stored. |
| D8 | The application services are the only entry point the console uses: one method per use case, returning domain objects for the console to format. | The console stays an adapter (`ARCHITECTURE.md`), and every use case checks Session, Permission and rules in one place. |
| D9 | A broken rule is reported with `RuleViolation` (in `enrollment.domain`) and its reason; the console writes `Error: <reason>`. Missing Session and missing Permission have fixed reasons (R6, R7). | One way to report errors, usable from value objects and services alike. |
| D10 | The docs drive the development: an agent learns the domain from `docs/domain/` and reads only the code files the file map in `modules.md` names. Every design choice is recorded here and in the model. | A new session, without memory, should not need to read the whole codebase to understand the design. |
| D11 | `SectionRepository` has an extra query `enrolledSection(StudentNumber, CourseCode): Optional<Section>` not in the original model. | `EnrollmentService` needs to find whether a student is already enrolled in a course (I19) and which section to call `changeGrades`/`unenroll` on (R32). A linear scan of all sections in the service would repeat in three places; one repository query is cleaner. Added to `model.puml` and `modules.md`. |
| D12 | `Building` exposes `findClassroom(int): Classroom` (package-visible helper). | `SectionService` needs to validate that the classroom exists when creating a section (I16), and `CampusService` needs it to modify/delete classrooms. Adding it to the aggregate avoids exposing the internal list. Added to `model.puml`. |
| D13 | `AccessService` exposes `session()` and `permissions()` accessors. | Other services need them to validate the session and construct the initial admin from `Main` without adding direct dependencies on the Session or Permissions objects. |
| D14 | `ConsoleLoop.handleLine` is package-private to allow direct unit testing without a reader. | Enables simpler tests that call one line at a time; no other class uses it. |
| D15 | The `Dispatcher` handles `Exit()` by returning `null`; `ConsoleLoop` treats `null` as the exit signal. | Keeps the exit logic in one place (the loop) without a separate checked exception path. |
| D16 | CR-1: `ModifySection` and `DeleteSection` instructions added. `MANAGE_SECTIONS` permission now covers create, modify, delete and query (was create and query). `Section.modify(Period, Day, CourseCode, ClassroomRef, ProfessorId)` mutates the mutable fields in place. `SectionRepository.remove(SectionCode)` removes a section. Cross-aggregate checks (enrolled count vs new capacity, course-change guard) live in `SectionService`. | These follow the same patterns as other modify/delete pairs already in the system. |
| D17 | CR-2: `QUERY_ENROLLMENTS` and `LOAD_FILE` actions added to `Action` and `Permissions`. `QUERY_ENROLLMENTS` is allowed for all user types; `LOAD_FILE` for admin only. | `StudentCourses` is allowed for students on their own number; splitting it from `MANAGE_ENROLLMENTS` avoids giving students the enroll/change-grades powers. |
| D18 | CR-2: `ReportService` added in `enrollment.application`. It holds the four report use cases (I25–I28). Each checks session and permission, then reads from repositories without changing anything. | A dedicated service keeps report logic separate from mutation logic, and the application layer is the right place for cross-aggregate reads. |
| D19 | CR-2: `FileLoader` added in `enrollment.console`. It reads the file, runs each line through the existing `ConsoleLoop.handleLine` path, collects error counts, and writes the summary. The `Load(path)` instruction is dispatched from `Dispatcher` which delegates to `FileLoader`. | Reusing `ConsoleLoop.handleLine` ensures the file lines follow exactly the same rules as console lines, with no duplication. |
| D20 | CR-2: `CourseStudentRow` and `StudentCourseRow` are record types returned by `ReportService` and formatted by `ResponseFormatter`. They carry the data the reports need without exposing raw domain objects across the service boundary. | Consistent with how the other services return domain objects for the console to format. |
| D21 | CR-2: `SectionRepository.ofClassroom(ClassroomRef)` is already named `usingClassroom`; used as-is for `ClassroomSections`. `SectionRepository.ofSemester` is not added; instead `ReportService` queries all sections and all courses and filters in the service. | Adding a new repository method for a one-off filter is a heavier change; the service filter is simpler and there is no performance requirement. |
| D22 | CR-3: `SectionChoicePolicy.choose` now picks the Section with the fewest enrollments among those with Room, breaking ties by lowest Section code. This replaces the R29 rule (lowest code only). The policy signature is unchanged. | Balanced sections distribute students evenly across available sections; ties are broken deterministically by code so the result is always the same given the same state. |
| D23 | CR-4: Grade scale changed to coursework 0–70, final exam 0–30, passing grade 65. Replaces D4/R28 for the grade numbers. Only `GradeScale` and its tests change; no other class knows these numbers (D4). | The School changed its grade scale; the policy is the single place to update. |
| D24 | CR-5: Prerequisites are stored inside `Course` as an ordered `List<CourseCode>` (the aggregate root) and also in `CourseRepository` via extra methods (`addPrerequisite`, `removeAllPrerequisites`, `prerequisitesOf`, `isPrerequisiteOfAny`). | Keeping the list on the aggregate makes `Course.prerequisites()` available without a repository call; the extra repository methods handle cross-aggregate checks (cycle detection uses all courses' prerequisites). |
| D25 | CR-5: Cycle detection in `CatalogService.addPrerequisite` does a BFS/DFS starting from the proposed prerequisite and checking whether it reaches the course being modified, using `CourseRepository.prerequisitesOf`. | Any cycle would mean the course transitively requires itself; BFS on the prerequisite graph is the standard approach. |
| D26 | CR-5: `CreditLimit` is a value class in `enrollment.domain.catalog` that holds the constant `MAX = 24`. `EnrollmentService` uses it to check the credit limit. | Keeps the magic number in one place (D4 pattern), consistent with how `GradeScale` holds grade numbers. |
| D27 | CR-5: `QueryCourse` output extended with `| prerequisites: <codes>` or `| prerequisites: none`. The formatter reads `course.prerequisites()` directly. | The prerequisite list is part of the aggregate; no new repository call needed. |
| D28 | CR-5: `EnrollmentService.doEnroll` checks prerequisites by calling `sections.enrolledSection(studentNumber, prereqCode)` and checking the grade with `GradeScale.passed`. Credit-limit check calls `catalog.currentCredits(sn)` which uses `sections.enrolledCourseCodes(sn)`. | Cross-aggregate check (I31, I32) lives in the application service (D5). |
| D29 | CR-5: `SectionRepository.enrolledCourseCodes(StudentNumber)` added. Returns the course codes the student is currently enrolled in; used by `CatalogService.currentCredits`. | One repository method avoids repeating the scan in multiple places; consistent with D11. Added to `model.puml`. |
| D30 | CR-6: `Period.overlaps(Period)` added. Two periods overlap when each starts strictly before the other ends (touching at an endpoint is not an overlap). The logic lives entirely in the value object. | Period is the right place for this rule; it needs no outside knowledge. Added to `model.puml`. |
| D31 | CR-6: `SectionRepository.enrolledSections(StudentNumber)` added. Returns the list of Sections the student is currently enrolled in; used by `SectionChoicePolicy` and `SectionService.modifySection`. | One repository method; consistent with D11, D29. Added to `model.puml`. |
| D32 | CR-6: `SectionChoicePolicy.choose` gains a third parameter `List<Section> enrolledSections` (the sections the student is already in). Sections that overlap any of those are excluded before the fewest-enrollments/lowest-code sort. The existing two-parameter callers are updated to pass the student's sections. | The policy is the right place for the selection rule; passing the enrolled sections keeps the policy pure (no repository access). Added to `model.puml`. |
| D33 | CR-6: Classroom and professor overlap checks in `SectionService` scan all existing sections with the same classroom/professor and reject if any overlaps the new section on the same day. The check runs after all field-validity checks, consistent with I6. For `ModifySection`, the enrolled-student overlap check (I36) also runs here, scanning each enrolled student's other sections. | Cross-aggregate rule (D5): no aggregate can see all sections; the service can. |
