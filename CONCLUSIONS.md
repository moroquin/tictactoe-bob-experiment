## 1. Summary

`without-ddd` and `with-ddd` built the same system from the same prompts. The DDD folder passed 95 of 104 cumulative hidden-scenario checks (91 %) against 12 of 104 (12 %) for the plain folder — a difference that persisted across every phase. The primary root cause in `without-ddd` is a single, permanent formatting bug (mutating responses printed with `OK:` prefix) that produced false-confidence green tests while every query-output scenario failed. `with-ddd` carried one persistent escape of its own (F1-03-syntax, a missing edge case on instruction parsing). Despite costing 1.78× more Bobcoins and 1.70× more time overall (39.73 vs. 22.35 Bobcoins; 1962 vs. 1153 s), `with-ddd` was dramatically more efficient per correct scenario (0.418 vs. 1.863 Bobcoins/scenario). Design quality diverged too: `with-ddd` held propagation cost flat at ~22 % while `without-ddd` was stuck at 34 % throughout; cohesion (TCC median 0.83 vs. 0.17) and encapsulation (1 exposed getter vs. 6–7) favoured `with-ddd` consistently. In the rule-change phases, `with-ddd` changed one class each time, the named policy that owns the rule (`SectionChoicePolicy` in F4, `GradeScale` in F5). `without-ddd` changed one class in F4 (an inline lambda in `EnrollmentService`) and two in F5, where the grade rule is split between `Enrollment` and `EnrollmentService`.

## 3. Coupling, cohesion and encapsulation

### 3.1 Efferent coupling (Ce) and propagation cost

`without-ddd` has 15 classes throughout F1–F7; Ce max is 11 in every phase (`service.EnrollmentService`). `with-ddd` starts with 49 classes; Ce max is 29 in F1 and grows to 31 from F3 onward (`application.EnrollmentService`, Ce 18–20; `application.ReportService`, Ce 26 in F3+). Despite `with-ddd` having higher Ce on the most-connected service class, the **propagation cost** is consistently lower: 34.2 % (`without-ddd`, all phases) versus 21.3 % (F1–F2), 23.0 % (F3–F5), 22.4 % (F6–F7) for `with-ddd`. The difference arises because `with-ddd`'s many small domain classes form a wide, shallow fan-out to stable value objects; `without-ddd`'s flat structure of 15 classes means each large class reaches a higher fraction of the system transitively.

The Ce max coupling in `with-ddd` is mostly to stable value objects (domain.RuleViolation Ca=21–23, domain.access.User Ca=12–17, domain.sections.Section Ca=8–10, domain.people.StudentNumber Ca=14–17). Coupling to these is cheap because they rarely change. `without-ddd`'s `service.EnrollmentService` (Ce 11) couples directly to every model class and the store; changes to any of those 11 classes can ripple to the service.

`without-ddd` has 10 low-cohesion classes (TCC < 0.5) throughout: all model domain objects (`model.Building`, `model.Classroom`, `model.Course`, `model.Enrollment`, `model.Professor`, `model.Section`, `model.Student`, `model.User`) plus `service.Result` and `store.Store`. These objects are anemic data holders — fields with getters/setters, no method groupings around related fields. `model.Section` (LCOM* 0.97–0.98, TCC 0.11–0.15, LCOM4 6) is the worst: 7 fields, 14 methods by F7, but the methods don't share fields cohesively.

`with-ddd` also has low-cohesion classes: `console.ResponseFormatter` (TCC 0.0, LCOM4 6–10 throughout) — it formats output for every entity type, so each method touches only its entity-specific fields; `domain.access.User` (TCC 0.27, LCOM4 2) — mixes identity and credential fields; `domain.sections.Section` (TCC 0.27–0.29, LCOM4 2–6) — still inherently multi-faceted, but LCOM4=2 vs. 6 shows better grouping than the plain version; `domain.catalog.Course` (TCC 0.21–0.30) — gains a prerequisite list in F6, which is not shared by all methods. LCOM4 > 1 classes: 12 in `with-ddd` (roughly stable), 10 in `without-ddd` (stable).

### 3.3 Yourdon & Constantine connections

Both folders hold the **worst overall connection type at "external"** throughout all phases (files/streams shared with Main). Neither reaches common or content coupling. Control connections (3 = a boolean/enum flag decides what the callee does) are stable at 2 per-folder throughout:

- **without-ddd**: `console.Console → service.EnrollmentService` (control: `Console.handleModifyUser` passes a flag to `modifyUser`; `Console.handleUser` passes a flag to `createUser`). These are real control couplings — `Console.handleModifyUser` dispatches to `EnrollmentService.modifyUser` with a type argument that decides which path the service takes. The 20-method block of `console.Console.handle* → console.Console.requirePermission` is intra-class control and does not count as inter-class coupling.
- **with-ddd**: `application.AccessService.requirePermission → domain.access.Permissions.allows` (true control: the return value of `allows()` decides whether to throw or continue); plus `console.Dispatcher.handleModifyUser/handleUser → application.AccessService.modifyUser/createUser` for the same reason as above. These are all structural and necessary; no workaround is present.

Y&C mean index: `without-ddd` holds at 1.43 from F2 onward; `with-ddd` holds at 1.4–1.43. The difference is negligible in absolute terms, but `with-ddd`'s wider set of stamp connections (to typed domain objects rather than primitive arguments) is structurally richer.

### 3.4 File and method size

`without-ddd` maxes at 416 lines in F1 (console.Console) and grows to 615 lines (service.EnrollmentService) by F7. `with-ddd` never exceeds 370 lines (console.Dispatcher) across all phases. `without-ddd` reaches 5 methods > 30 lines in F7 (`EnrollmentService.modifySection` 56 lines, `Console.handle` 54 lines, `Console.handleLoad` 43 lines, `Parser.parseArgs` 38 lines, `EnrollmentService.createSection` 31 lines). `with-ddd` reaches 6 methods > 30 lines only in F7 (`SectionService.modifySection` 49, `Dispatcher.dispatch` 47, `InstructionParser.parseArgs` 43, `EnrollmentService.doEnroll` 38, `Main.main` 37, `SectionService.createSection` 33). `without-ddd` consistently exceeds `with-ddd` on median constructor parameter count; both have too many in their main service classes.

### 3.5 Most coupled and least cohesive classes

**Most coupled, `without-ddd`**: `service.EnrollmentService` — Ce 11 to every model class and the store; Ca 2 (Console and Main only). By F7 it is 615 lines with 43 methods. Every domain rule lives here: enrollment, sections, users, professors, students, buildings, classrooms, courses, reports, file loading, prerequisites, time conflicts. Adding any rule always touches this class.

**Most coupled, `with-ddd`**: `application.EnrollmentService` — Ce 18–20 (uses nearly all domain repositories and services), Ca 2. `application.ReportService` has Ce 26 in F3–F7 (reads many domain types to build reports). Neither grows in line count after F6 (96 lines, 5 methods vs. 118 lines, 4 methods). The high Ce in these classes is mostly coupling to stable value objects.

**Least cohesive, `without-ddd`**: `model.Section` (TCC 0.11–0.15, LCOM4 6, LCOM* 0.97–0.98). It has 7 fields (code, period, day, course, classroom, professor, enrollments) and 14 methods, but most methods touch only one or two fields. `store.Store` (TCC 0.11, LCOM4 9) holds all nine entity collections in separate fields, each only touched by its own add/query methods.

**Least cohesive, `with-ddd`**: `console.ResponseFormatter` (TCC 0.0, LCOM4 6–10, LCOM* 1.0). It has one shared field (`dateFormat`) and 10 format methods, each dedicated to a different entity — no two methods share a field, hence TCC = 0. This is an intrinsic property of the formatter role.

### 3.6 Encapsulation

`without-ddd` exposes 6–7 mutable state getters throughout all phases: `model.Classroom.getBuilding()`, `model.Enrollment.getSection()`, `model.Enrollment.getStudent()`, `model.Section.getClassroom()`, `model.Section.getCourse()`, `model.Section.getProfessor()`, `service.EnrollmentService.currentUser()`. The `getEnrollments()` method on `Section` returns the raw `ArrayList<Enrollment>`, and `EnrollmentService.doEnroll()` calls `target.getEnrollments().add(new Enrollment(...))` directly — bypassing any capacity rule that might exist in a dedicated enroll method. The capacity check in `Section.hasRoom()` is done before selecting the section, so the bypass is caught, but a caller could skip `hasRoom()` and add directly.

`with-ddd` exposes one mutable state getter: `application.AccessService.session()` returns `domain.access.Session` (a mutable object). Domain entities use `modify()`-style methods: `Section.modify(...)`, `Course.modify(...)`, `User.modify(...)` — callers cannot modify individual fields without going through these methods, which enforces invariants. The `domain.sections.Section.enrollments()` method (a record accessor) returns a `List`, but enrollment is done through the service and repository, not by direct list mutation.

`with-ddd` has 11–13 public state-changing methods in service/domain versus 18–23 in `without-ddd`, reflecting a narrower public interface.

## 6. Accuracy

### 6.1 Failed scenarios and the rules they break

**`without-ddd` persistent failures (F1–F7):** Six of the seven F1 scenarios fail with the same root cause: every mutating operation prints `OK: <message>` but the scenarios expect the response without the `OK:` prefix (e.g., expected `1 | admin | admin`, got `OK: 1 | admin | admin`). This is a single implementation decision (R41 says the text after `OK:` is free, but without-ddd Bob treated all responses as free-text `OK:` messages, including queries whose outputs are fixed by R1–R7). F1-03-syntax fails because `without-ddd` rejects a valid instruction as `Error: invalid instruction` where the expected output is `OK`.

**`with-ddd` persistent failure (F1–F7):** F1-03-syntax line 38: expected `Error: invalid instruction`, got `OK: student created`. The instruction parser in `with-ddd` passes an instruction that should fail the R40/R33 check (a bare keyword that looks like a student-create command). This failure persists because the `InstructionParser` never received a fix for that edge case; the gap decision (A6 in F1) only addressed the long-number ambiguity, not the specific failing line.

**F6 new failure (with-ddd):** F6-01-prerequisites line 57: expected `Error in line 2`, got `Error in line 1: invalid instruction`. The file-load error counting counts one line differently; the prerequisite logic in `with-ddd` (F6) processes the correct cycle/deletion behaviour in direct-console mode but the file-load path uses a different error-line numbering.

**F7 carryover from F6 (with-ddd):** F6-01-prerequisites persists through F7 (line 56, same issue). F7-01 and F7-02 pass for `with-ddd`.

### 6.2 Expected lines matched

`with-ddd` matched 99.7–99.9 % of expected lines across all phases; `without-ddd` matched 89.7–93.7 %. The gap in `without-ddd` is entirely from the `OK:` prefix on query responses — the underlying data logic is correct, but the output format diverges on every query line.

### 6.3 Scenarios of earlier phases (regression and rule-change compliance)

`with-ddd`: 6/7 in every phase for the F1 batch (1 escape from the syntax scenario). All new-phase scenarios are correctly carried. No regression introduced.

`without-ddd`: 0/7 F1 scenarios pass in any later phase (same root cause). The F3 and later scenarios that `without-ddd` passes (1 scenario by F3, 2 by F4–F5, 3 by F6–F7) are the file-load and report scenarios whose output format happens not to include `OK:` on the checked lines, or match despite the prefix.

### 6.4 Bob's tests vs. hidden scenarios (escapes and false alarms)

All of Bob's own tests pass in every phase for both folders (100 %). However, they all show **false confidence**:
- `without-ddd` escapes grow from 7 (F1) to 18 (F7) — Bob's tests never catch the `OK:` prefix bug because they test through the service API directly (not console output), so the test output matches the service's logic rather than the console's formatting.
- `with-ddd` holds at 1 escape throughout F1–F5, rising to 2 in F6–F7 (the prerequisites file-load numbering issue and the syntax edge case). Bob's tests in `with-ddd` are console-level integration tests (ConsoleIntegrationTest) that do catch most issues, but the specific failing lines in the hidden scenarios test edge cases not covered.

### 6.5 Mutation score

`without-ddd` mutation score (without console): 65 % (F1) → 77 % (F7), rising with each phase as test coverage deepens. `with-ddd`: 56 % (F1) → 65 % (F7). `without-ddd` consistently kills more mutants relative to the non-console code. This does not translate to better scenarios because `without-ddd`'s tests test domain logic (EnrollmentService directly) while missing the console formatting contract. `with-ddd`'s tests are integration-focused but give lower mutation scores because many domain value objects (repositories, value types) are not individually targeted.

### 6.6 Own decisions that could diverge from expected behaviour despite green scenarios

- **`without-ddd` F1 A3** (R24 period validation, hours 1–12, no leading zeros): `without-ddd` rejects `07:10am` as an invalid period. The scenarios may not test this boundary; if a hidden scenario uses a leading-zero period, `without-ddd` would reject a valid instruction.
- **`without-ddd` F6 A1** (grade threshold "61 or more" vs. existing "65 or more"): R28 in its `REQUIREMENTS.md` still showed the original 61, because CR-4 (F5) changed the rule to 65 and `without-ddd` never updates the docs. It kept 65, which is the correct value after CR-4, so this decision does not cause a failure. It shows the risk of stale requirements when the agent does not maintain the docs.
- **`with-ddd` F1 A4** (`Dispatcher` returns `null` for `Exit()` as a sentinel): if any scenario issues `Exit()` and expects a specific output, `with-ddd` would print nothing — but R41 says `Exit()` produces no output, so this is consistent.
- **`with-ddd` F6 A5** (OK response text `"OK: prerequisite added"`): the text after `OK:` is free (R41), so this cannot cause a scenario failure, but if the test expected specific text it would diverge.

## 7. Efficiency and scalability

### 7.1 Correct scenarios against cost and time

Cumulative across F1–F7: `with-ddd` delivered 95 correct scenarios for 39.73 Bobcoins (0.418 per scenario); `without-ddd` delivered 12 for 22.35 Bobcoins (1.863 per scenario). `with-ddd` is 4.5× cheaper per correct scenario despite costing 1.78× more in absolute terms.

### 7.2 Propagation cost trend

`without-ddd` propagation cost is exactly 34.2 % in every phase. The flat line indicates the design did not change structurally: 15 classes, same coupling topology, adding code to existing classes rather than abstracting. `with-ddd` rose from 21.3 % (F1–F2) to 23.0 % (F3–F5, when `ReportService` was added with Ce 26) then settled to 22.4 % (F6–F7) as new classes replaced connections within the existing structure rather than adding broad new ones.

### 7.3 Y&C index trend

`without-ddd`: 1.39 (F1) → 1.43 (F2–F7), stable. `with-ddd`: 1.39 (F1) → 1.40 (F2–F3) → 1.41 (F6) → 1.43 (F7). Both converge to 1.43 in F7. The index is dominated by data connections (passing simple values), which are correct. Neither folder degraded toward control or common coupling.

### 7.4 Bobcoins per 100 lines touched

`without-ddd` spiked to 46.4 in F4 (5 lines changed, 2.32 Bobcoins — very small change, high fixed cost ratio) and 15.17 in F5. `with-ddd` spiked to 22.2 in F5 (10 lines, 2.22 Bobcoins). In F2 and F3 `with-ddd` was more expensive per touched line (3.8 vs. 2.02; 2.18 vs. 1.56). In F6 and F7 it was cheaper (2.8 vs. 3.68; 5.97 vs. 7.27). The trend after F5 is that `with-ddd` becomes more cost-effective than `without-ddd` per line of change.

### 7.5 Cohesion and code reads over time

`with-ddd` TCC median rose from 0.78 in F1–F2 to 0.83 from F3 onward and held there. Code reads before editing: `with-ddd` needed fewer in F4 (2 code files) due to `modules.md` pointing directly at the change location. In F6–F7 (cross-cutting rules), `with-ddd` read more code (8–12 files) because the new invariants touched multiple layers, but the documentation reduced re-reading by providing a map.

`runs/stats.md` does not exist (only one execution per folder); no medians are available to confirm which differences repeat across runs.

## 10. Verdict

`with-ddd` is unambiguously better at **building correctly** (91 % vs. 12 % hidden scenarios across phases) and at **changing a single rule cheaply** (F4: 1 class in both, but in `with-ddd` it is a named policy; F5: 1 class vs. 2 classes; fewer Bobcoins in both phases: 2.01 vs. 2.32 and 2.22 vs. 2.73). For **cost efficiency per correct scenario** it is 4.5× cheaper despite costing 1.78× more in absolute Bobcoins. The DDD documentation contributed: a shared vocabulary (all 40–41 glossary terms present), a file map that let the agent navigate to the right file immediately in F4 and F5, and a decisions log that made prior patterns reusable in F6–F7. The cost it imposed was primarily in F1 (8.86 vs. 2.36 Bobcoins to build the initial design) and in large structural phases (F3, F6) where reading and updating docs added time. `without-ddd` is better at **absolute cost minimisation** when correctness is not required, and produces a **higher mutation score** (77 % vs. 65 % in F7) because its tests target domain logic directly — but that mutation score coexists with 18 hidden-scenario escapes, which reveals the tests do not cover the specification.

## 11. Limits

1. **Single execution per folder.** Every difference in this analysis is an observation of one run; the same code and the same agent can produce different choices in another session. Three to five executions would be needed to establish which differences are systematic.

2. **Bob writes its own history.** The session histories in `history/session-<n>.md` are written by the agent itself. The types of decisions ("ambiguity", "gap", "design") are self-classified. An agent can misclassify or omit decisions. Every cited decision was cross-checked against the actual code (e.g., `SectionChoicePolicy.java` F4 verified the comparator matches the stated decision; `EnrollmentService.doEnroll()` F4 verified the inline rule matches the stated decision), but the completeness of the decision log cannot be guaranteed.

3. **Two confounded variables in `with-ddd`.** The folder received both the DDD documentation (glossary, model, invariants, policies, modules, decisions) and a workflow instruction (`AGENTS.md`: docs drive development, edit docs before code, update file map). The measured differences reflect the combination of both. It is not possible from this data alone to separate the effect of the documentation content from the effect of the docs-first workflow.

4. **DDD docs prescribe a design.** The invariants, model, and modules documents specify aggregates, repositories, application services, and a specific package layout. The design metrics (propagation cost, cohesion, coupling) measure that prescribed design. The metrics do not tell us whether an equally good design was possible without the docs; they confirm that the agent followed the prescribed structure.

5. **`without-ddd`'s dominant error is a formatting decision.** The 12/104 correct scenario count for `without-ddd` is overwhelmingly determined by a single early decision (R41 applied to query output). A corrected version would likely pass far more scenarios, making the accuracy comparison less stark. The design and scalability comparisons (propagation cost, cohesion, encapsulation) would remain valid regardless.

6. **Mutation score and scenario accuracy are uncorrelated.** `without-ddd` has a higher mutation score but far fewer passing scenarios. The scenarios test the specification contract; the mutation score tests the test suite's sensitivity to code mutations. A test suite that tests service logic directly can have a high mutation score while missing specification-level contracts, as observed here.
